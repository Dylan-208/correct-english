Um corretor de inglês
que mora no seu Windows.

Você seleciona um texto, aperta Ctrl + C três vezes, e uma janelinha aparece com a tradução para português, a versão corrigida e um botão Replace que troca o texto no lugar. Enquanto você digita, palavra errada ganha o mesmo sublinhado vermelho que você já tem em português.

Este documento é o plano antes do código: os mockups, de onde vem a correção, e uma avaliação honesta de qual parte é difícil — porque uma delas é bem difícil.

Windows 11 repo público 3 camadas de correção MVP útil em ~1 semana 1 parte de risco alto
Mockup 1 · o fluxo principal

A janelinha do Ctrl+C ×3

É a tela que você descreveu. Aparece perto do cursor, some com Esc, e o Replace devolve o texto corrigido direto no campo onde você estava.

Correct English Ctrl+C ×3 ×
Selecionado · 24 palavras

Português
Eu te enviei o relatório ontem. Você poderia confirmar se está tudo certo com os números?
Correção
I sent you the report yesterday. Could you confirm whether everything looks correct with the numbers?

Replace ↵ Copiar Alternativas Opus 5 · 1,4 s

O Replace é a parte esperta: como você chegou aqui com Ctrl+C, o texto já estava no clipboard. Para devolver, o app volta o foco para a janela anterior, põe a correção no clipboard, dispara Ctrl+V e restaura o que estava no clipboard antes. Funciona na grande maioria dos apps.

Por que o triple Ctrl+C é uma boa escolha

Ele resolve de graça o problema mais chato: ler o texto selecionado de qualquer aplicativo. Sem isso, seria preciso interrogar o app pelo UI Automation do Windows — que falha em Electron, terminal, Figma, jogos. O clipboard funciona em tudo que tem seleção.

O detalhe de implementação: não dá para “registrar” Ctrl+C como atalho global, porque isso engoliria o copiar normal do sistema. Precisa de um hook passivo de teclado (WH_KEYBOARD_LL) contando três toques em menos de ~600 ms, sem bloquear a tecla.

Mockup 2 · enquanto você digita

O sublinhado vermelho

Igual ao print que você mandou: a palavra errada fica com a ondinha vermelha e, ao passar o mouse ou apertar o atalho, aparece a sugestão. Essa é a parte difícil — a seção “A parte difícil” mais abaixo explica por quê e quais são os caminhos.

Nova mensagem — sarah@client.com
Hi Sarah,

I will send you the informations about the meeting tomorrow. Please let me know if you needs anything else
Enviar 2 sugestões
informations → information local

Information é incontável em inglês — não tem plural. Vale para advice, feedback, research, software.

Aceitar Ignorar Adicionar ao dicionário

As duas sugestões acima vêm de camadas diferentes: informations é dicionário local (instantâneo, offline, custo zero) e needs→need é regra de concordância. Nenhuma das duas precisou chamar a IA — e é assim que se digita sem lag e sem queimar dinheiro.

O aviso que precisa ser dito

Um hook global de teclado é, tecnicamente, um keylogger. É a mesma API. Então esse projeto tem obrigações que não são opcionais:

  • Buffer só na RAM, só a frase atual, nunca em disco.
  • Zero teclas enviadas para a internet — a IA só é chamada com a seleção, sob comando seu.
  • Detectar campo de senha (ES_PASSWORD / UIA IsPassword) e parar de gravar.
  • Código aberto justamente para isso ser auditável.
  • Sem assinatura de código, o SmartScreen vai reclamar na instalação. Certificado depois.
A pergunta central

De onde vem a interpretação correta

Resposta curta: de três lugares diferentes, e nenhum dos três resolve sozinho. Ortografia vem de um dicionário local. Gramática vem de regras. Significado e naturalidade vêm de um modelo de linguagem. Tentar fazer o LLM cuidar das três coisas dá um app lento e caro; tentar fazer só regras dá um app que não entende o que você quis dizer.

O que cada camada realmente entrega

L0 — dicionário local. Hunspell é o corretor que já roda no LibreOffice, Firefox e Chrome. Dicionário en_US livre (SCOWL), ~50 mil palavras, carrega em memória em milissegundos. Combinado com SymSpell para sugerir a correção por distância de edição. Pega recieve, informations, alot, successfull. Não pega “their” onde devia ser “there” — as duas existem no dicionário.

L1 — regras. LanguageTool é open source (LGPL), você roda o servidor localmente e conversa por HTTP em localhost. É o que resolve o caso do “their/there”, concordância verbal, artigo faltando, preposição errada. Custa um servidor Java parado consumindo ~1 GB de RAM — o preço de ser offline e ilimitado.

L2 — o modelo. É a única camada que entende. Ela sabe que “I have send the report to you” é gramaticalmente quase defensável mas soa estrangeiro, e que um nativo escreveria “I sent you the report”. Também é a única que consegue traduzir e explicar o erro em português.

O contrato com o modelo

O truque para isso não virar “texto solto que eu preciso parsear”: pedir saída estruturada. A Messages API valida o JSON contra um schema, então o app nunca recebe uma resposta que não caiba na tela.

// output_config.format — o app só aceita isto
{
  "traducao_pt":    string,
  "texto_corrigido": string,
  "tom":            "neutro" | "formal" | "informal",
  "correcoes": [{
    "de":     string,
    "para":   string,
    "tipo":   "ortografia" | "tempo_verbal"
             | "preposicao" | "artigo"
             | "naturalidade" | "pontuacao",
    "porque": string  // em português, 1 frase
  }],
  "alternativas": string[],  // outras 2 formas
  "confianca":    number
}

Três ajustes que mudam a sensação de uso:

  • Streaming. A tradução chega primeiro e já aparece na tela enquanto a correção ainda está sendo gerada. Reduz a espera percebida de 2 s para ~400 ms.
  • Effort baixo. No Opus 5 o raciocínio é ligado por padrão. Para uma frase de e-mail isso é desperdício — output_config.effort: "low" corta latência e custo sem perder qualidade nessa tarefa. (Melhor do que desligar o thinking, que no Opus 5 tem efeitos colaterais chatos.)
  • Prompt caching. O prompt de sistema é fixo e pode ser cacheado — mas só cacheia a partir de ~1024 tokens de prefixo. Vale escrever um prompt de sistema generoso, com exemplos de erros típicos de brasileiro, e cachear.

Escolha do modelo — números reais

Base de cálculo: prompt de sistema ~600 tokens, seleção de ~80 palavras (~110 tokens), resposta JSON ~300 tokens. Volume estimado de 40 consultas por dia útil (~880/mês). Dólar a R$ 5,40.

Avaliação de risco

A parte difícil

Você suspeitou que a interpretação do texto seria o mais complicado. É o mais importante, mas não é o mais difícil — esse problema está resolvido pelas três camadas acima.

O mais difícil é o sublinhado vermelho. Não porque detectar o erro seja difícil, mas porque desenhar uma ondinha dentro do campo de texto de outro programa exige saber onde cada palavra está na tela — e o Windows não entrega isso de forma confiável. É aqui que o Grammarly gasta a maior parte da engenharia dele, e é a maior fonte de reclamação dos usuários dele.

Só depois de tudo funcionar.

A recomendação

Não tente o D nem o E agora. A combinação A + B + C entrega quase toda a experiência que você descreveu, com risco baixo: o popup do Ctrl+C×3 funciona em todo lugar, a bolha no caret te avisa em tempo real em todo lugar, e a ondinha vermelha de verdade aparece exatamente onde você escreve mais inglês — no navegador.

Se depois de usar por um mês o buraco que sobrar for “quero a ondinha no Outlook desktop e no Word”, aí o D vale o investimento, e só para esses dois apps — que são justamente onde o UIA funciona bem.

Decisão pendente

Com o que construir

Isso não é um app web com um wrapper. Metade do trabalho é hook de teclado, foco de janela, clipboard, overlay topmost e UI Automation — API do Windows crua. A escolha de stack pesa mais aqui do que num projeto normal.

No seu PC agora: node 24.18 git 2.55 python 3.14 — e não tem dotnet, cargo nem java instalados.

Execução · ordem importa

As fases

Ordenadas para você ter algo que você mesmo usa o mais cedo possível. A Fase 2 já é um app que ganha o seu dia; tudo depois é ampliar cobertura.

FASE 0

Repositório e decisões registradas

1 dia

Repo público, licença MIT, README com o mockup, e docs/adr/ com as três decisões que travamos aqui: stack, motor de correção, caminho do sublinhado. ADR curto, 10 linhas — o objetivo é você lembrar em dezembro por que escolheu assim.

FASE 1

O esqueleto: atalho, janela, Replace

2–3 diassem IA ainda

Hook detectando Ctrl+C×3, popup aparecendo perto do cursor, e o Replace funcionando com uma correção falsa e fixa (ex: sempre trocar por MAIÚSCULAS). Parece bobo, mas valida a parte que mais quebra: guardar o HWND anterior, devolver o foco, colar, e restaurar o clipboard. Se isso funcionar em Chrome, Slack, Word e VS Code, o resto é fácil.

FASE 2

Camada L2: o app fica útil

3–4 diasmarco: uso diário

Claude Opus 5 com saída estruturada e streaming, tradução + correção + explicação em português, seletor de tom, chave da API guardada no Windows Credential Manager (não em arquivo de config), cache local por hash do texto para não pagar duas vezes pela mesma frase. A partir daqui você já usa todo dia.

FASE 3

Camadas L0 e L1 + a bolha no caret

~1 semana

Hunspell embarcado, LanguageTool local opcional, lista de permissão por app, detecção de campo de senha, e o aviso discreto perto do cursor (caminho B). É o “me avisa enquanto digito”, sem depender de mapear pixels.

FASE 4

Extensão de navegador: a ondinha de verdade

~1 semana

Extensão Chrome/Edge com sublinhado real no DOM, hovercard do Mockup 2, e ponte WebSocket com o app desktop para reusar as três camadas. Aqui a experiência fica igual ao print que você mandou.

FASE 5

Distribuição

2–3 dias

Instalador (Inno Setup ou MSIX), auto-update, ícone na bandeja, iniciar com o Windows, GitHub Actions publicando a release. Certificado de assinatura quando incomodar o suficiente.

FASE 6

Overlay nativo — só se ainda fizer falta

aberto

UIA + overlay (caminho D) mirando só Outlook e Word, onde o UIA é confiável. Decisão a tomar depois de um mês de uso real, não agora.
